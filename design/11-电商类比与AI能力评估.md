# 11-电商类比与AI能力评估

**这篇解决什么问题:** 方案持有者问了两个战略问题:①这是不是一个类似"电商小店铺"的项目(能不能直接复用电商轮子)?②把 AI 能力加进去,会不会更高效做出产品、更 scalable(更多客户/品类),并借 AI agent 能力快速增长?本篇给判断:**像电商的只有皮,骨架是赊销台账;AI 加在四个刀刃上收益真实,但有三条红线,且 AI 不改变 M0→M1 的开工顺序。**

## 一、是不是电商小店?——皮像,骨不像

表面看确实像:有商品(SKU)、有下单、有履约(配送)、有客户管理——很像微信小商店/有赞微商城。但五个承重结构全都相反:

| 维度 | 电商小店 | 本项目 |
|---|---|---|
| 交易模型 | **先款后货**,单次成交,购物车+在线支付闭环 | **先货后款(赊销)**,持续供货关系,收款是事后核销 |
| 需求入口 | 买家自助浏览下单(storefront 是核心) | 语音/聊天**卖家代录**(storefront 基本不存在) |
| 定价 | 公开统一价 | **一户一价**、日牌价、时价面议——熟人议价 |
| 信任凭据 | 平台担保、支付即凭据 | **签字回执、三联单、对账单**——凭据链是全案灵魂 |
| 参与方 | 买卖两方 | 四方(店/员/客/供)+ 员工监督链 |

**结论:内核是"应收台账(AR)+ 轻履约",不是"订单-支付-履约"的电商内核。** 硬套电商开源(Medusa/Saleor/WooCommerce 类)会背上大量用不上的复杂度(购物车、营销、物流商对接),而命根子(赊销台账/回执/对账)恰恰是它们没有的——这正是我们自研账务内核、其余全用轮子的分界线,与 design/10 的选型纪律一致。

**电商世界里真正值得抄的三个概念**(抄概念,不搬平台):①B2B 电商的 **per-customer price list**(按客户价目表)——正是"一户一价"的成熟建模,M2 定价模块照此设计;②订单状态机与 SKU/品类树建模(已在用);③credit limit(信用额度)在 B2B 电商里的拦截/提示交互。另外留一个口子:客户端"再来一单"本质是一个微型 storefront-lite,将来年轻采购员多了,可借电商 UI 做一页轻菜单——M3 之后的可选项,不进主线。

### 业务不同,技术栈高度雷同——约八成直接借鉴

把"业务模型"和"技术栈"分开看,结论立刻清晰:**电商小店的技术栈几乎就是我们的技术栈**,踩过的坑都是现成答案:

| 技术层 | 电商小店的成熟做法 | 我们的对应(现状) | 借鉴度 |
|---|---|---|---|
| 多租户 SaaS 架构 | tenant_id 贯穿+行级隔离 | 同(design/02,已在 schema/中间件执行) | ★★★ 全借 |
| 小程序前端 | TDesign/Vant 组件库、分包、授权流 | 同一套工具链 | ★★★ 全借 |
| 后端形态 | Serverless/边缘函数+API网关+会话 | Workers+Hono(design/10) | ★★★ 全借 |
| 数据建模 | SKU/品类树/订单状态机/价目表 | 同构,直接照抄建模套路 | ★★★ 全借 |
| 图片与CDN | 对象存储+CDN(商品图) | R2(回执照片) | ★★★ 全借 |
| 微信消息触达 | 订阅消息攒授权、卡片分享的全部实践 | 同样的规则同样的坑,电商已交过学费 | ★★★ 全借 |
| 微信支付 | 服务商进件/回调/对账的完整方案 | M3 自动核销直接抄电商服务商实践 | ★★☆ 大部分借 |
| 管理后台 | Vue admin 骨架(表格/表单/权限) | PC 工作台底座(M2) | ★★☆ 骨架借,页面自建 |
| 交易/账务内核 | 购物车-支付-履约 | **赊销台账(自研,不借)** | ☆ 不借 |

值得研读的开源参照(读架构与微信集成层,不搬业务):国内开源商城(crmeb/likeshop 类,"小程序+admin+api"三层结构与微信生态集成最贴近县域场景)、Medusa(插件化与 per-customer 价目)、微信官方小商店实践。**一句话:技术栈上我们就是一个"电商小店同款工程",只是把它的交易内核换成了赊销台账内核——八成的路别人已铺好,自研的两成恰是护城河。**

## 二、AI 加在哪:四个刀刃

判断标准仍是那把标尺(design/09):让老板娘少干几分钟、少错几次。按 ROI 排序:

**刀刃① 订单结构化(最高优先,M2)。** "把一段口语转成结构化订单"就是大模型的本职。现规则版拆单 POC 在合成语料 90%,真实语料的方言、连读、黑话长尾靠规则穷举不现实;LLM 拿着该客户的常用品对照表做结构化输出,能把"红格率"显著压低。**机制不变**:AI 只产生候选,拿不准照样标红,老板娘点确认才生效——AI 让红格变少,不让确认消失。成本可承受:每单约几厘到几分钱(示例),日均 30 单每月几元。

**刀刃② 回执照片预检(M3)。** 视觉模型读手写签字回执,与系统单据比对金额/数量,不一致自动亮出来——把"差异闸门"从纯人工升级为"AI 预检+人工确认",装错漏装的事后发现更早一步。现 OCR 评估项(design/06 M3)升级为 VLM 评估。

**刀刃③ 催款军师话术(M3,已设计)。** design/08 已定:规则引擎先行,LLM 按付款画像生成个性化话术三选一——只出主意,发不发永远老板点头。

**刀刃④ 行业模板接入提速(M3+)。** 新行业接入最贵的是词表/品类树/行规访谈整理;把摊主访谈录音丢给 AI 生成配置草案、人工定稿,接入成本再降——但**样板店共创不可省**:"死蟹谁担"这种行规 AI 编不出来,得问干这行的人。

**开发侧与运营侧的 AI(不进产品)**:用 AI coding agent 加速开发本身(本仓库即是实证),1~2 人团队的产出杠杆是真实的,M1 工期有压缩空间;上线后用 AI 做用户答疑库("怎么改价"之类),降教学成本。

## 三、三条红线(热情越高越要钉死)

1. **AI 不进账务路径。** 金额计算、挂账、核销、对账永远是确定性代码(app/core),模型只在"理解人话"和"生成人话"两端工作。模型幻觉出一个 SKU 或一个数量,必须被规则校验拦下标红——这条已落成代码(`app/core/splitter-ai.js`:AI 候选逐条过规则校验,查无此货/数量非法/单位不符一律标红)。
2. **AI 不替人做决定。** 确认订单、给不给折扣、催不催款,docs/10 的自动化边界原文有效;"AI agent 自动对账自动催款"听着性感,违背的恰是本产品的信任根基。
3. **合规与数据边界。** 客户经营数据喂境外模型有数据出境问题——结构化任务优先用国内模型 API 或本地小模型,Cloudflare Workers AI 只处理不含敏感经营数据的任务;面向用户的生成内容(话术)留人工确认环节。产品叙事上**不打"AI 记账"招牌**——县城老板对 AI 无感甚至警惕(docs/09:不说数字化转型),AI 是后厨的刀,不是门头的招牌。

## 四、对"更 scalable"的诚实回答

- **更多品类**:scalable 的根是行业模板六维度(design/03),AI 降低的是模板的**边际接入成本**(刀刃④),不是替代模板机制;
- **更多客户**:增长瓶颈在触达(微信规则)、付费意愿(365元验证)、地推(人)——这三样 AI 都帮不上,M0 打靶一项不能少;
- **更快做出产品**:真。AI 辅助开发 + 不重复发明轮子(design/10)+ 账务内核已全绿,M1 有把握比排期快;
- **follow AI 行业**:接口层面留好口子(LLM provider 可换、prompt 与对照表分离),模型进步自动兑现为红格率下降——**吃 AI 的红利,不赌 AI 的叙事**。
