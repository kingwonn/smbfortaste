# 16-收单守护与自动化边界

**这篇解决什么问题:** 方案持有者的硬要求——**收单必须自动化**:愿意换习惯的客户可以走 bot/小程序/公众号,但很多商家(客户)不愿改;要用 computer use 或其他本地 PC/AI 方式,把"客户照旧发微信"变成"店侧自动进需求清单"。本篇给出"收单守护"方案:三种模式的风险光谱、技术架构、与 computer use 的关系、以及不许逾越的边界。核心增量提取逻辑已落码带测(`app/watcher/`)。

## 一、定位:自动化落在店侧,客户零感知

店里那台**本来就整天开着微信电脑版**的电脑(照片证据:拢账时电脑/收款音箱都在),加装一个"收单守护"程序,盯着微信窗口把新到的订货消息自动送进收单箱——客户那头什么都不用变。与 design/15 的关系:15 的四层是"人搭把手"的通道,本篇把其中的人工动作也自动掉;公众号/小程序仍是愿意迁移客户的正规自助通道,两路并行。

## 二、三种模式:风险光谱上从零到低

| 模式 | 做法 | 老板娘动作 | 风险 | 语音 |
|---|---|---|---|---|
| **C·通知捕获** | 读系统通知弹窗文本(OS 能力) | 零 | ≈0(纯读OS通知) | 显示[语音],回落A |
| **A·伴读(默认)** | 她点开会话,守护自动读屏(OCR/VLM)、增量识别新消息、进收单箱 | **每会话点一下** | ≈0(纯读屏,零输入注入) | 她右键"转文字",守护自动读转写 |
| **B·全自动(computer use)** | 守护自动点开未读会话、自动右键转文字,全链零人工 | 零 | **低但非零**(模拟人类点击,按键精灵级;不碰内存/协议) | 自动转文字后读取 |

- 模式 A 的账要算清:她现在每条消息要"读→记→誊",伴读模式降为"点一下",90% 的活已经没了,且风险为零——**默认档**;
- 模式 B 默认关闭,风险告知后店主自选开启;点击节奏模拟人类(随机间隔),只在白天工作时段运行;
- **手机补充通道**:Android 通知监听 App(OS 合规能力)捕获微信通知文本,短消息零操作进箱,与 PC 守护互为备份。

## 三、红线(重申,永不越)

**协议 bot / hook / dll 注入 / 改内存,一律不碰**——她全部客户关系都在那个微信号上,封号=生意归零,任何工程收益都不值这个赌注。模式 B 的"模拟点击"是边界内的最后一档:只产生和人手一样的 UI 事件,不读写微信进程内部。

## 四、架构:捕获层可换,提取层不变

```
[捕获层] 屏幕截图(Windows Graphics Capture)/系统通知/computer use 视觉
    ↓ 产出"会话快照" {chatTitle, day, messages:[{side, text}]}
[提取层] IncrementalExtractor(app/watcher/extract.js,已落码)
    连拍去重·增量识别·滚屏防误报·噪声过滤·只收对方消息
    ↓ 新消息(按会话合并,客户名前置)
[推送层] POST /api/intake(source: screen-watch)
    ↓
收单箱 → 拆单 → 需求todolist(标红置顶)→ 确认
```

- **提取层是唯一平台无关、可离线压测的部分**,已带 7 个测试:连拍零重复、同文重发补收、滚屏回看不重发、跨天重置、噪声(时间戳/[图片])过滤、只收对方消息;
- 捕获层三选(按模式):本地 OCR(PaddleOCR,中文强、离线、零成本)起步;VLM(识别更稳、能读复杂排版)按量付费;**computer use 智能体驱动模式 B**(视觉理解 UI+决策点击,微信改版也不怕)——三者产出同一快照格式,换引擎不换逻辑;
- 已知盲区(诚实注记):同文本消息在旧消息滚出屏外后再来一条可能漏收——极罕见;模式 A 下人在看屏,模式 B 由捕获层锚定滚动位置规避;
- 隐私边界:守护只处理白名单会话(建档客户),截图即弃不留存,识别文本只进自家收单箱。

## 五、computer use 的位置

Claude computer use(及同类视觉智能体)= 模式 B 的引擎:看屏→找未读→点开→(语音)右键转文字→读内容→回到列表。它的价值在**鲁棒性**(UI 改版、弹窗、异常都能视觉应对)而非成本(截图+推理按次计费,比本地 OCR 贵)。落地策略:**A 模式用本地 OCR 打底(每天 0 成本),B 模式用 computer use 做原型验证,跑稳后再评估是否用"OCR+固定坐标点击"降成本**。守护跑在店里电脑上,数据不出本机(除识别 API 调用,白名单+脱敏)。

## 六、排期与验收

| 项 | 期次 | 验收(示例) |
|---|---|---|
| 提取层(已落码) | 本次 | 7 测试全绿 ✅ |
| 模式 A:截屏+PaddleOCR+推送 | M2 | 店里真机:一晚 30 条消息,伴读捕获率≥95%,误收 0 |
| 模式 C:通知捕获 | M2 | 短消息零点击进箱 |
| 模式 B:computer use 原型 | M2 末 | 连续 3 晚零人工全自动,无异常点击;店主签风险知情 |
| Android 通知监听 App | M3 | 手机端短消息进箱,与 PC 去重 |
| 公众号收单(自愿客户) | M2/M3 | design/15 第 4 层不变 |

---

**一句话压住本篇**:自动化全部压在店侧——伴读模式零风险拿掉九成人工,computer use 驱动的全自动档给想要"一下都不点"的店主自选;协议与注入的红线一寸不让,客户那头,永远什么都不用变。
